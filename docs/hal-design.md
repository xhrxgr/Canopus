# HAL：让模块不认识固件

> 这份文档回答一个问题：**Canopus 要怎么改，才能"加一台设备"从两周变成两天。**

## 1. 先纠正一个常见误解

"广泛设备支持"经常被理解成"把固件地址收集齐"。地址确实是前提，但**它已经被解决了** ——
`canopus-target-private` 按 target 选表，模块不用知道 `bt_create_bond` 在 `0xc805...`。

真正让新设备卡住的是**语义差异**，这些数字地址解决不了：

| 差异 | 043 的值 | 换一台设备可能变成 |
|---|---|---|
| L2CAP 事件号 | `DATA_IND = 7` | 9 / 11 / 枚举顺序全不同 |
| 连接完成结构里 CID 的位置 | `+108`（远端 `+110`） | `+76`，或者根本没有这个结构 |
| 绑定状态的"已绑定" | 聚合 3、设备级 2 | 只有 1，或者语义反过来 |
| 回调怎么装 | 镜像 17 词表、只改配对槽 | 有独立的 `register_xxx_callbacks` |
| 数据到底走不走回调 | 事件 7 | 可能要主动 poll |
| 传输类型参数 | `CLASSIC = 1` | `0` |

这些都是 BandLink 的 `platform.rs` 里现在的硬编码。**HAL 的职责就是把它们关进一个文件。**

## 2. 分层

```
┌──────────────────────────────────────────────┐
│ 模块（bandlink043）                            │
│   只写：hal::bt::connect(...) / Event::Data    │
│   不出现任何固件数字                            │
└───────────────────┬──────────────────────────┘
                    │  语义
┌───────────────────▼──────────────────────────┐
│ canopus-hal                                    │
│   Event / BtError / ConnectRequest / 接口函数   │
│   把"要什么"翻译成"调哪个后端函数"              │
└───────────────────┬──────────────────────────┘
                    │  每台设备一份
┌───────────────────▼──────────────────────────┐
│ backend/<target>                               │
│   事件号映射表、结构偏移、回调装配、状态归一     │
│   ← 唯一允许出现固件数字的地方                   │
└───────────────────┬──────────────────────────┘
                    │  地址（已解决）
┌───────────────────▼──────────────────────────┐
│ canopus-target-private（符号包生成）            │
└──────────────────────────────────────────────┘
```

**上层不认识固件，下层不认识业务。** 两条都不能破。

## 3. 为什么是"链接期"而不是"运行期"

HAL 不等于 vtable。模块是静态链接进固件的，backend 由 feature 在编译期选定，
调用点直接单态化成 `bl` —— 没有函数指针表、没有运行期查找、没有 RAM 开销。

```rust
// bt.rs
#[cfg(feature = "backend-band10pro-043")]
use crate::backend::band10pro_043 as backend;

pub fn discovery_start() -> Result<(), BtError> { backend::discovery_start() }
```

这一点很重要：**零成本才是嵌入式里能被接受的抽象**，否则等于用 RAM 换整洁，没人会同意。

## 4. 新设备要做什么（三步）

1. **符号**：`targets/<id>/symbols/*.json` 补齐（`fw-match` + `symbol-generator` 已有工具链）
2. **后端**：写 `backend/<id>.rs`，实现 `bt` 的语义契约（不实现就编译不过）
3. **feature**：`Cargo.toml` 加 `backend-<id>`，把 target 链进来

模块代码 **一行不改**，包括 BandLink。

## 5. 硬失败发生在哪里

三层防线，越靠前越省事：

| 时机 | 拦什么 | 现在的状态 |
|---|---|---|
| 写 manifest 时 | 模块声明 `classic.discovery`，target 没这能力 → 规划期就拒 | ✅ 已接（`canopus build` 会报 `lacks required capabilities`） |
| 编 HAL 时 | 选了没有后端的目标 → `BtError::Unsupported`，或 trait 未实现编译失败 | 🟡 已搭骨架 |
| 链接时 | 后端引用了不存在的固件符号 → 未定义符号 | ✅ 原有机制 |

## 6. 迁移步骤（不推翻现有代码）

| 步 | 内容 | 风险 |
|---|---|---|
| S1 | 建 `canopus-hal` 骨架 + 043 后端（事件映射、绑定归一、扫描） | 无，纯新增 |
| S2 | 把"连接请求构造"搬进后端（68 字节结构、`config` 内联在 +24） | 中：动的是能跑通的代码，需真机回归 |
| S3 | 把"发送 / 收到帧的切分"搬进后端（`StockBuffer` 12 字节前缀、`+4+offset`） | 中 |
| S4 | BandLink 删掉 `platform.rs` 里所有固件常量，改调 `hal::bt` | 低，行为不变 |
| S5 | 036 写第二个后端，验证"模块零改动"这个承诺 | —— |

**S1 已经完成**（`sdk/rust/canopus-hal`，`cargo check` 通过）。
S2/S3 才是真正的工作量，也是唯一能让 036/030 跑起来的路径。

## 7. 一个反面教训

前面几轮里，我们花了很长时间在"猜 043 的某个地址"上（`--discard-locals`、
符号名裁剪、按 44 字节步长切封装族）。结果是：地址不是瓶颈，
**"这个固件的语义和上一台差在哪"才是**。

HAL 的价值不在于让代码好看，而在于把一个"每次都要重新逆向"的问题，
变成"每次只需要填一张表"的问题。
